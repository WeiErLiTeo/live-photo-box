## 📖 基本概念

实况照片（Live Photo / Motion Photo / Micro Video）由一张静态图片与一段短视频组成。拍摄时设备记录按下快门前后约 1.5~3 秒的画面，浏览时可播放动态效果。

各厂商的实现按**打包方式**分为两类：

| 类型 | 打包方式 | 厂商 |
|------|----------|------|
| **单文件** | 一个 `.jpg` 文件：JPEG 图片数据在前，MP4 视频数据拼接在后，视频位置由 XMP 元数据中的偏移量/长度字段指定 | Google、OPPO、小米、三星 |
| **单文件（私有）** | 一个 `.heic` 或 `.jpg` 文件，不使用 XMP 标准，通过私有二进制标记定位视频 | 华为 Moving |
| **双文件** | 一个图片文件 + 一个视频文件，两者通过元数据中的 `ContentIdentifier` UUID 配对 | Apple Live |
| **双文件（私有）** | 一个 `.jpg` + 一个 `.mp4`，通过 vivo 私有 ID 关联（旧格式，≤X200 系列） | vivo（≤X200 系列） |

单文件格式的核心机制：JPEG 的 XMP（Adobe Extensible Metadata Platform）元数据中记录了视频的长度（字节数），图片部分长度 = 文件总大小 − 视频长度。XMP 数据存储在 JPEG 的 APP1 段中。

双文件格式由于图片与视频本就是独立文件，不存在"定位视频"的问题；核心机制是**元数据配对**——照片和视频共享相同的 `ContentIdentifier` UUID。

## 📦 单文件格式

单文件格式的通用二进制布局：

```
┌──────────────────────┐  ← 文件起始 (offset 0)
│   JPEG 图片数据       │
│   (含 EXIF + XMP)    │
├──────────────────────┤  ← 图片结束位置
│   MP4 视频数据        │
└──────────────────────┘  ← 文件末尾

```
各协议的区别在于 XMP 元数据中使用的命名空间和字段不同。

### Google MicroVideo V1

Google 最早的实况照片格式，已弃用，但旧设备（旧 Pixel、MIUI 时代的小米）仍大量使用。


#### 二进制结构

与通用布局一致。JPEG 尾部直接拼接 MP4（ftyp=mp42/isom）。


#### XMP 元数据

使用 `GCamera` 命名空间，自闭合 `rdf:Description` 标签，共 4 个数据属性：

```xml
<rdf:Description rdf:about=""
    xmlns:GCamera="http://ns.google.com/photos/1.0/camera/"
    GCamera:MicroVideo="1"
    GCamera:MicroVideoVersion="1"
    GCamera:MicroVideoOffset="4424761"
    GCamera:MicroVideoPresentationTimestampUs="459334"/>

```

#### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `GCamera:MicroVideo` | 整数 | 实况照片标识。值为 `1` |
| `GCamera:MicroVideoVersion` | 整数 | 协议版本，固定为 `1` |
| `GCamera:MicroVideoOffset` | 整数 | 视频字节数。从文件末尾向前推算：图片长度 = 文件总大小 − 此值 |
| `GCamera:MicroVideoPresentationTimestampUs` | 整数 | 封面帧在视频中的微秒时间戳。`0` = 视频开头 |


#### 提取逻辑

1. 读取 `MicroVideoOffset` 值
2. 图片部分 = 文件前 `totalSize − MicroVideoOffset` 字节
3. 视频部分 = 文件后 `MicroVideoOffset` 字节


#### 封面帧机制

`GCamera:MicroVideoPresentationTimestampUs` 直接给出封面帧在视频中的微秒位置。例如值为 `459334` 即视频第 0.46 秒处为封面。值为 `0` 表示封面在视频开头。

### Google MotionPhoto V2

Google 的现代实况照片标准。使用 `Container:Directory` 结构化 XMP 描述文件内容。目前兼容性最广，Windows 11 文件资源管理器可原生预览。

- 规范名称：**Motion Photo format 1.0**
- 官方文档：<https://developer.android.com/media/platform/motion-photo-format>

使用者：Google Pixel、三星 Galaxy、小米（HyperOS）、摩托罗拉等。


#### 二进制结构（JPEG）

JPEG 图片数据在前，视频数据（MP4 或 MOV）直接追加在 JPEG EOI（`FF D9`）之后，无分隔符。

规范要求：Container:Directory 中各 Item **必须**按其在文件中出现的实际顺序排列，且紧密排列（tightly packed）。`MotionPhoto` Item **必须**位于文件末尾，其后**不允许**有任何其他字节。


#### XMP 元数据

使用 `GCamera`、`Container`、`Item` 三个命名空间。注意：官方规范中 Camera 命名空间的**默认前缀**为 `Camera`，但各厂商实现普遍使用 `GCamera`——XMP 以 URI 为准，前缀可任意，二者等价。

```xml
<rdf:Description rdf:about=""
    xmlns:GCamera="http://ns.google.com/photos/1.0/camera/"
    xmlns:Container="http://ns.google.com/photos/1.0/container/"
    xmlns:Item="http://ns.google.com/photos/1.0/container/item/"
    GCamera:MotionPhoto="1"
    GCamera:MotionPhotoVersion="1"
    GCamera:MotionPhotoPresentationTimestampUs="1230275">
  <Container:Directory>
    <rdf:Seq>
      <rdf:li rdf:parseType="Resource">
        <Container:Item Item:Mime="image/jpeg"
                        Item:Semantic="Primary"
                        Item:Length="0"
                        Item:Padding="0"/>
      </rdf:li>
      <rdf:li rdf:parseType="Resource">
        <Container:Item Item:Mime="video/mp4"
                        Item:Semantic="MotionPhoto"
                        Item:Length="4424761"
                        Item:Padding="0"/>
      </rdf:li>
    </rdf:Seq>
  </Container:Directory>
</rdf:Description>

```
> MicroVideo V1 的四个字段（`MicroVideo`、`MicroVideoVersion`、`MicroVideoOffset`、`MicroVideoPresentationTimestampUs`）在本规范中**已删除**，解析时**必须忽略**。视频定位应使用 `Container:Directory` 中的 `Item:Length`，而非 V1 的 `MicroVideoOffset`。


#### 字段说明

**Camera 元数据**（命名空间 `http://ns.google.com/photos/1.0/camera/`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `MotionPhoto` | `Integer` | `0` = 不是 Motion Photo；`1` = 是 Motion Photo。**其他值均视为未定义，等效于 `0`**。由于多数图片编辑器会保留 XMP，即使视频已被移除，该字段仍可能残留值为 `1`。因此该字段**不是决定性证据**——阅读器必须实际确认视频是否存在。 |
| `MotionPhotoVersion` | `Integer` | 协议版本。本规范定义为 `1`。 |
| `MotionPhotoPresentationTimestampUs` | `Long` | 封面帧在视频中的微秒时间戳。可为 `-1` 表示未设置。 |

**Container 元数据**（命名空间 `http://ns.google.com/photos/1.0/container/`）：

`Container:Directory` 是一个有序的 `rdf:Seq` 结构。**有且仅有一个** `Primary` Item，且必须排在第一位。

**Item 元数据**（命名空间 `http://ns.google.com/photos/1.0/container/item/`）：

| 属性 | 类型 | 说明 |
|------|------|------|
| `Mime` | `String` | **必填**。MIME 类型：`image/jpeg`、`image/heic`、`image/avif`、`video/mp4`、`video/quicktime` |
| `Semantic` | `String` | **必填**。`Primary`=主图片（有且仅有一个），`MotionPhoto`=实况视频（有且仅有一个），`GainMap`=Ultra HDR 增益图（可选） |
| `Length` | `Integer` | 次级 Item **必填**。资源字节长度。Primary Item 应为 `0`（图片长度由 MIME 类型解析确定）。视频的 `Length` 使阅读器可直接从文件末尾倒退 `<Length>` 字节定位视频起点。 |
| `Padding` | `Integer` | 仅 Primary Item 可有此属性。JPEG 格式下可选。表示主图片编码结束到下一媒体项之间的填充字节数。 |

> 实践观察：小米 14 Pro（HyperOS）的原厂样本中，Primary Item 缺少 `Item:Length` 与 `Item:Padding` 属性。Google 规范允许解析器通过 JPEG 自身确定主图片长度，因此实现时应对此情况做容错处理。


#### 封面帧机制

`MotionPhotoPresentationTimestampUs` 指定封面帧在视频中的微秒位置。例如 `1230275` → 视频第 1.230275 秒。

**该字段缺失时的默认行为**（官方规范明确定义）：阅读器应使用视频时长**除以 2**，选择最接近中点的时间戳前一帧作为封面——**不是**"自行选择"。


#### V2 相比 V1 的改进

| | MicroVideo V1 | MotionPhoto V2 |
|------|:---:|:---:|
| 资源描述 | 单一 `MicroVideoOffset` 字段 | `Container:Directory` 结构化目录 |
| MIME 类型 | 隐式 | 显式声明（`image/jpeg`、`video/mp4`、`video/quicktime` 等） |
| 可扩展性 | 不可扩展 | `rdf:Seq` 可添加更多资源项（如 Ultra HDR GainMap） |
| 填充支持 | 无 | `Item:Padding` 支持 |
| V1 兼容字段 | — | 规范要求忽略 V1 的四个字段 |
| 当前状态 | 已弃用 | 现行标准 |

### 小米 Mi-Live Photo

小米直接使用 Google 标准协议（早期 MIUI → MicroVideo V1；当前 HyperOS → MotionPhoto V2），**无独立协议**。小米相册完全依赖 V2 识别和播放实况照片，不限制读取自家元数据——符合 V2 标准的其他品牌（如 OPPO）实况照片均可播放。


#### 二进制结构

与 Google V2 一致——JPEG 图片在前，视频追加在文件末尾。较新机型可能包含 GainMap 增益图：

```
┌──────────────────────┐
│   JPEG 图片           │
│   (含 EXIF + XMP)     │
├──────────────────────┤
│   GainMap 增益图      │  ← Ultra HDR，非实况照片协议内容
├──────────────────────┤
│   MP4 视频            │
└──────────────────────┘

```

#### XMP 元数据

完全使用 Google MotionPhoto V2 标准，无私有扩展字段。`Container:Directory` 中除 Primary 和 MotionPhoto 外可能包含 GainMap Item（HDR 增益图，与实况无关）。

小米额外写入一个 `MiCamera` 命名空间（`http://ns.xiaomi.com/photos/1.0/camera/`），当前格式为 `MiCamera:XMPMeta`，内容为 XML 编码的 `video_madrid_image` 元数据。该字段 `offset="0" length="0"`，**不参与视频定位**——视频定位完全由 V2 的 `Item:Length` 决定。🔴 早期 HyperOS 版本是否使用 `MiCamera:VideoLength` 待确认。

```xml
<rdf:Description rdf:about=""
    xmlns:GCamera="http://ns.google.com/photos/1.0/camera/"
    xmlns:Container="http://ns.google.com/photos/1.0/container/"
    xmlns:Item="http://ns.google.com/photos/1.0/container/item/"
    xmlns:MiCamera="http://ns.xiaomi.com/photos/1.0/camera/"
    GCamera:MotionPhoto="1"
    GCamera:MotionPhotoVersion="1"
    GCamera:MotionPhotoPresentationTimestampUs="1533248"
    MiCamera:XMPMeta="&lt;video_madrid_image type=&quot;701&quot;
      offset=&quot;0&quot; length=&quot;0&quot;
      width=&quot;3072&quot; height=&quot;4096&quot;
      paddingx=&quot;86&quot; paddingy=&quot;86&quot;
      location_enabled=&quot;0&quot; time_enabled=&quot;0&quot; dark=&quot;0&quot; /&gt;">
  <Container:Directory>
    <rdf:Seq>
      <rdf:li>  <!-- Primary: image/jpeg -->
      <rdf:li>  <!-- GainMap: image/jpeg（HDR，与实况无关） -->
      <rdf:li>  <!-- MotionPhoto: video/mp4 -->
    </rdf:Seq>
  </Container:Directory>
</rdf:Description>

```

#### 私有 EXIF 标签

| Tag (Hex) | IFD | 内容 | 与实况相关？ |
|-----------|-----|------|:---:|
| `0x010f` Make | IFD0 | 固定为 `"Xiaomi"` | 否 |
| `0x0110` Model | IFD0 | 设备型号 | 否 |
| `0x9a00` XiaomiModel | IFD0 | 小米内部型号名 | 否 |
| `0x889e` | ExifIFD | JSON 设备信息（`buildDevice`、`livephotoInfo`、`waterLogo` 等），详见下方 | 否 |
| `0x8895` | ExifIFD | `0`（版本标记，🔴 "新=3"说法待验证） | 🔴 |
| `0x8889` | ExifIFD | `"HDR"` | 🔴 |
| `0x8897` | ExifIFD | `1` | 🔴 |
| `0x889a` | IFD0 + ExifIFD | `0` | 🔴 |
| `0x889d` | IFD0 + ExifIFD | `"Madrid"`（相机功能代号） | 🔴 |
| `0x889f` | ExifIFD | `0` | 🔴 |
| `0x88a2` | IFD0 | 浮点数组（传感器数据） | 🔴 |
| `0x88a3` | IFD0 | `{}` | 🔴 |


#### 0x889e JSON 内容

```json
{
  "buildDevice": "popsicle",
  "customize": "",
  "livephotoInfo": "tailShakeI:97 head:14447250877 time:14449050877 tail:14450590877
                    filterId:66048 onlyPreDuration:false  offset:266752 tailOffset:934708 ",
  "version": 2,
  "waterLogo": "XIAOMI",
  "waterName": "17 Pro Max"
}

```
| 字段 | 说明 | 与实况相关？ |
|------|------|:---:|
| `buildDevice` | 设备代号 | 否 |
| `customize` | 自定义标记（旧版为 `cvLensName` + `filterName`） | 否 |
| `livephotoInfo` | 拍摄元数据（`head`/`time`/`tail` 为系统时钟值，`offset`/`tailOffset` 为字节偏移）。合成时可填 0 占位 | 否 |
| `version` | JSON 格式版本 | 否 |
| `waterLogo` / `waterName` | 水印标识 / 设备名 | 否 |

> 🔴 `livephotoInfo` 中 `tailShakeI`、`headShakeI`、`onlyPreDuration` 字段用途待确认，与实况照片协议无关。


#### JPEG 私有段

| 段标记 | 大小 | 内容 | 与实况相关？ |
|--------|------|------|:---:|
| APP3 `ALGO_COMMON` | ~20-24 KB | ISP 算法处理数据 | 否 |
| APP3 `OISINFO` | ~0.2-8 KB | OIS 光学防抖数据 | 否 |
| APP4 `XIAOMI_CUSTOMIZE` | ~640-770 B | 私有 EXIF 标签值冗余存储（JSON） | 否 |
| APP5 `CLOUD_WATER` | ~450 B | 🔴 用途待确认 | 🔴 |
| APP5 `XMI Camera Data` | 2 段，~65KB + 变长 | zlib 压缩相机数据 | 否 |

> APP3/APP4/APP5 各段均为相机 ISP 管线数据，与实况照片协议无关。


#### 实用性结论

合成小米可用的实况照片**使用 Google MotionPhoto V2 协议即可**。小米相册不限制读取自家元数据，符合 V2 标准的其他品牌实况照片均可播放。如需小米相册完整显示型号和水印，额外写入 `Make`、`Model`、`0x889e` 三个字段即可。

### OPPO O-Live Photo

OPPO / OnePlus 在 Google MotionPhoto V2 基础上扩展的私有协议。完全兼容 V2，同时增加 OPPO 独有字段。使用者：OPPO ColorOS、OnePlus OxygenOS。


#### 二进制结构（OPPO 原厂文件）

OPPO 原厂文件比标准 V2 多了一个尾部区域：

```
┌──────────────────────┐
│   JPEG 图片           │
├──────────────────────┤
│   GainMap 增益图      │  ← HDR 相关，非实况照片协议内容
├──────────────────────┤
│   MP4 视频            │
├──────────────────────┤
│   OnePlus 尾部数据    │  ← 仅 OnePlus 机型，约 846 KB
└──────────────────────┘

```
人工合成的文件通常不含 OnePlus 尾部。


#### XMP 元数据

在 V2 基础上新增 `OpCamera` 命名空间，增加 5 个属性：

```xml
<rdf:Description rdf:about=""
    xmlns:GCamera="http://ns.google.com/photos/1.0/camera/"
    xmlns:Container="http://ns.google.com/photos/1.0/container/"
    xmlns:Item="http://ns.google.com/photos/1.0/container/item/"
    xmlns:OpCamera="http://ns.oplus.com/photos/1.0/camera/"
    GCamera:MotionPhoto="1"
    GCamera:MotionPhotoVersion="1"
    GCamera:MotionPhotoPresentationTimestampUs="2762000"
    OpCamera:MotionPhotoOwner="oplus"
    OpCamera:OLivePhotoVersion="2"
    OpCamera:VideoLength="8275393"
    OpCamera:MotionPhotoPrimaryPresentationTimestampUs="1466388"
    OpCamera:MotionPhotoEnable="True">
  <Container:Directory>
    <rdf:Seq>
      <rdf:li rdf:parseType="Resource">
        <Container:Item Item:Mime="image/jpeg" Item:Semantic="Primary"
                        Item:Length="0" Item:Padding="0"/>
      </rdf:li>
      <rdf:li rdf:parseType="Resource">
        <Container:Item Item:Mime="video/mp4" Item:Semantic="MotionPhoto"
                        Item:Length="9121768" Item:Padding="0"/>
      </rdf:li>
    </rdf:Seq>
  </Container:Directory>
</rdf:Description>

```
> Container:Directory 结构与 V2 一致——Primary 和 MotionPhoto 两个 Item。实际样本中 OPPO 文件可能包含第三个 GainMap Item（HDR 增益图），但与实况照片协议无关。


#### OpCamera 新增字段

| 字段 | 说明 |
|------|------|
| `OpCamera:MotionPhotoOwner` | 所有者标识，固定为 `"oplus"`。OPPO 相册据此判断是否为自家拍摄 |
| `OpCamera:OLivePhotoVersion` | O-Live 协议版本，当前为 `"2"` |
| `OpCamera:VideoLength` | 纯视频字节数（不含 OnePlus 尾部）。原厂文件中 `Item:Length` = 视频+尾部，`VideoLength` = 纯视频。合成时两者相等 |
| `OpCamera:MotionPhotoPrimaryPresentationTimestampUs` | 主照片（原始拍摄帧）的微秒时间戳。原厂文件中与 `MotionPhotoPresentationTimestampUs` 相同；更换封面后，前者保持原值不变（指向原始拍摄帧），后者更新为新封面位置。两者分别记录"拍摄的那一帧"和"当前封面帧" |
| `OpCamera:MotionPhotoEnable` | 封面编辑标记。原厂文件无此字段；在 OPPO 相册中编辑封面后写入，值为 `True`。可用于判断封面是否被用户修改过 |


#### 封面帧机制

OPPO 是唯一拥有**双时间戳**的协议，可区分"当前封面帧"和"原始拍摄帧"：

| 字段 | 含义 | 换封面后 |
|------|------|----------|
| `GCamera:MotionPhotoPresentationTimestampUs` | 当前封面帧在视频中的微秒位置 | **更新**为新封面位置 |
| `OpCamera:MotionPhotoPrimaryPresentationTimestampUs` | 原始拍摄帧（按下快门那一刻）的微秒位置 | **保持不变** |

原厂文件中两者相同。更换封面后，第一个字段变为新封面位置，第二个字段保留原始值。这是其他协议不具备的能力——可以同时知道"现在的封面在哪"和"当初拍摄的那一帧在哪"。


#### EXIF UserComment 标记

除 XMP 外，OPPO 相册还会检查 EXIF 中的 `UserComment` 字段：

```
UserComment = "oplus_10485792"
              │      │
              │      └── 最大视频字节数（10 MB）
              └── OPPO 前缀标识

```
不同机型该值可能不同：8388608 (8 MB)、10485792 (10 MB) 均有过出现。

若缺少此标记，OPPO 自带相册不会播放动态效果。Google Photos 和 Windows 11 不受影响——仅检查 XMP。

### 华为 Moving Photo

华为实况照片协议完全独立于 Google/OPPO/Apple 标准，**不使用 XMP 元数据**，通过私有二进制标记来标识和定位视频数据。华为提供两种容器格式——HEIC（内嵌 MP4）和 JPEG（中段嵌入 MP4）。

#### 官方 SDK 与 API

华为对外提供了两套实况照片接口，但**均不公开二进制格式细节**。

**LivePhotoKit SDK**（Android，HarmonyOS 4.3，Mate 70 系列 / Mate X6）：

| API | 功能 |
|-----|------|

| `LivePhotoInfo.getVideoOffset()` | 获取视频偏移量（= `getImageLength()`，即图片在前、视频紧跟） |

### <a id="huawei-heic"></a>华为 Moving Photo（HEIC）

华为 HEIC 实况照片是 ISOBMFF 单文件容器，采用 HEIF 规范的多轨道布局。静态图片区（HEIC）在前，内嵌视频区（完整 MP4）在后。`LIVE_` 尾标是实况照片判定标记（华为开发者论坛确认）。`tmap` brand 存在于所有华为相机 HEIC 文件（含非实况照片），不是实况照片专属标记。


#### 容器结构

定位方式：搜索第二个 `ftyp` box（major brand=`mp42`），即嵌入 MP4 的起点，而非依赖固定偏移量。

```
┌──────────────────────────────────────────┐ ← offset 0
│  ftyp box (28 bytes)                     │
│  major_brand = "heic"                    │
│  compatible   = "heic" + "mif1" + "tmap" │ ← ⚠️ tmap 非实况专属
├──────────────────────────────────────────┤
│  meta box                                │
│  ├─ hdlr: "pict" (Picture handler)       │
│  ├─ iloc: item location table            │
│  ├─ iinf: item info entries              │
│  │   ├─ infe: mime=PRIVATE (HDR gain map)│
│  │   ├─ infe: Exif                       │
│  │   └─ infe: DfxData (depth effect)     │
│  ├─ iref: item references                │
│  ├─ hvcC: HEVC still config              │
│  └─ hvcC: HEVC still config (alt res)    │
├──────────────────────────────────────────┤
│  mdat box — 静态图片 HEVC 数据             │
│  (多分辨率: 1024×1024, 1536×2048,          │
│   3072×4096, 4:2:0 8-bit Full Range)      │
├──────────────────────────────────────────┤ ← mdat 结束 = 嵌入 MP4 起点
│  ╔════════════════════════════════╗       │
│  ║  嵌入的完整 MP4 文件            ║       │
│  ║  ┌──────────────────────────┐ ║       │
│  ║  │ ftyp (mp42/iso2/mp42)    │ ║       │
│  ║  │ free                     │ ║       │
│  ║  │ mdat — 视频/音频数据       │ ║       │
│  ║  │ moov                     │ ║       │
│  ║  │  ├─ Track 1: vide (HEVC) │ ║       │
│  ║  │  ├─ Track 2: soun (AAC)  │ ║       │
│  ║  │  ├─ Track 3: meta        │ ║       │
│  ║  │  │  timed_metadata,      │ ║       │
│  ║  │  │  handler="com.open-   │ ║       │
│  ║  │  │  harmony.timed_       │ ║       │
│  ║  │  │  metadata.movingphoto"│ ║       │
│  ║  │  └─ udta -> ©too =       │ ║       │
│  ║  │     "Openharmony6.1"     │ ║       │
│  ║  └──────────────────────────┘ ║       │
│  ╚════════════════════════════════╝       │
├──────────────────────────────────────────┤
│  尾部 (60 bytes)                          │
│  v6_f39  953:1553  LIVE_NNNNNNN           │
└──────────────────────────────────────────┘ ← EOF

```

#### ftyp 品牌标识

| 字段 | 值 | 含义 |
|------|-----|------|
| Major Brand | `heic` | HEVC Still Image（声明为静态图片） |
| Minor Version | `0` | — |
| Compatible Brand 1 | `heic` | 标准 HEVC 静态图片 |
| Compatible Brand 2 | `mif1` | MIAF Image File Format |
| Compatible Brand 3 | `tmap` | 华为相机 HEIC 通用 brand，非实况专属 |

> Major Brand 声明为 `heic`（静态图片），导致 Windows 照片、Google Photos 等标准播放器仅解码静态图片。只有华为相册扫描 `LIVE_` 尾标后加载嵌入的 MP4。


#### 嵌入的 MP4 视频

HEIC 容器的 `mdat` 之后嵌入完整 MP4 文件，偏移不固定（取决于静态图片大小）。定位方式：搜索第二个 `ftyp` box（major brand=`mp42`）。

MP4 ftyp：`major=mp42`, `compat=iso2, mp42`

| Track | Handler | 编码 | 说明 |
|-------|---------|------|------|
| Track 1 | `vide` | HEVC (hvc1), 1920×1440 | 视频轨 |
| Track 2 | `soun` | AAC | 音频轨 |
| Track 3 | `meta` | `com.openharmony.timed_metadata.movingphoto` | 标记轨道，**非必需**——干净 MP4 + `LIVE_` 即可正常播放 |

> Track 3 不携带媒体数据（`nmhd` Null Media Header），推测为原生相机自动附加，连拍模式无此轨道仍被识别为实况照片。


#### MP4 内 udta 元数据

`moov` → `udta` → `©too` = `Openharmony6.1`（编码器字符串，非 `LIVE_` 标记）。

`moov` → `udta` → `meta` → `ilst` 含 5 个 `com.openharmony.*` 键：

| Key | 含义 | 示例值 |
|-----|------|--------|
| `com.openharmony.covertime` | 转换时间参数 | 二进制字符串，非纯 ASCII |
| `com.openharmony.deferredVideoEnhanceFlag` | 延迟视频增强标志 | `2` |
| `com.openharmony.encParam` | 编码参数 | `video_encode_bitrate_mode=SQR:bitrate=15000000:…` |
| `com.openharmony.starttime` | 拍摄起始时间戳 (ms) | `1784894929076` |
| `com.openharmony.videoId` | 视频 ID | `20260724200850212` |

> `com.openharmony.*` 键均为 HarmonyOS 私有元数据，**非必需**——干净 MP4 + `LIVE_` 即可正常播放。

`LIVE_` 标记位于嵌入 MP4 的 moov box 结束之后的文件尾部。HEIC 和 JPEG 格式一致，固定 **60 字节**：

```
v6_fXX            PPP:QQQQ            LIVE_NNNNNNN
```

| 偏移 (相对 moov 结束) | 字节数 | 内容 | 含义 |
|-----------------------|:---:|------|------|
| [+0..+5] | 6 | `v6_fXX` | **封面帧序号**（XX=视频中第几帧）。换封面后 Gallery 更新此值，编辑器进度条读它定位 |
| [+6..+19] | 14 | 空格填充 | — |
| [+20..+27] | 8 | `PPP:QQQQ` | **原始封面帧毫秒时间戳 : 原始视频毫秒时长**。只读历史记录，换封面后不变 |
| [+28..+39] | 12 | 空格填充 | — |
| [+40..+51] | 12 | `LIVE_NNNNNNN` | 实况照片判定标记，`NNNNNNN` = 嵌入 MP4 大小 **+16**（+16~+20 均可） |
| [+52..+59] | 8 | 空格填充 | — |

> 关键验证：同张照片改 fYY 从 37→80 → 编辑器进度条从中间跳到末尾，确认 **fYY 控制编辑器封面帧位置**。批量测试（44 个文件）证实 LIVE_ 接受 MP4+16 到 MP4+20 范围。6 组相机直出样本确认 PPP:QQQQ 为只读原始拍摄记录。


#### 封面帧

华为的封面帧**不是**一个参数或指针，而是**文件中的静态图片本身**。

```
┌─────────────────────────────────┐
│  HEIC 容器 / JPEG 图片           │
│  └─ 静态图片（多分辨率 HEVC）    │  ← 这就是封面帧！
├─────────────────────────────────┤
│  嵌入的完整 MP4 视频（不裁切）    │  ← 视频永远完整保留
├─────────────────────────────────┤
│  60 字节尾部                     │
└─────────────────────────────────┘
```

**改封面的实际流程**（基于合成文件改封面对比实验）：
1. 从视频中**抽取**用户选中的那一帧 → 编码为 JPEG → **替换**文件前半段静态图
2. 视频**不裁切**、完整保留，以不同参数重新编码
3. 尾部 `PPP:QQQQ` 保留原始值不动，`fYY` 更新为新封面帧号，`LIVE_` 更新为新 MP4 大小

**结论**：提取封面帧 = 提取静态图片。换封面 = 替换静态图片 + 更新 fYY + 更新 LIVE_。视频不裁切。

> fYY 即 `getCoverPosition()` 返回的帧序号，是华为协议中**唯一控制编辑器封面位置的字段**。PPP:QQQQ 为只读原始拍摄记录，换封面后不变。


#### EXIF 辅助检测标记

| 字段 | 值 | 用途 |
|------|-----|------|
| Make | `HUAWEI` | 辅助判断华为设备 |
| MakerNote | `##**N4031`, `Auto` | 华为相机内部型号代码 |
| Image Description | `_cuva` | 华为相机内部标记 |

> 以上 EXIF 标记为相机通用字段，非实况照片专用。仅 `LIVE_` 尾标是实况照片判定标记。


#### 提取逻辑

**提取静态图片**：解析 ISOBMFF 盒子树 → `meta` → `iloc` 定位全分辨率图像 → 解码 HEIC → 转 JPEG/PNG。

**提取视频**：

```
ftyp_pos = find_second(data, "ftyp", major="mp42")   // 找嵌入 MP4
video_start = ftyp_pos - 4                            // MP4 box size
moov_pos = rfind(data[video_start:], "moov")          // 找 moov box
moov_size = read_u32(data, video_start + moov_pos - 4)
video_end = video_start + moov_pos + moov_size        // MP4 结束（不含尾部）
video = data[video_start : video_end]                  // 完整 MP4
image = data[0 : video_start]                         // HEIC 静态部分

```

### <a id="huawei-jpeg"></a>华为 Moving Photo（JPEG）

华为 JPEG 实况照片与 Google Motion Photo "JPEG + 尾部追加 MP4" 不同——视频嵌入在文件中间。官方 SDK `getImageOffset() = 0`、`getVideoOffset() = getImageLength()` 确认了"图片在前、视频在后"的基本布局。

```
┌──────────────────────────────────────────────┐ <- offset 0
│  一级 JPEG 图片                               │
│  ├─ SOI (FFD8)                               │
│  ├─ APP1 (EXIF)                              │
│  │   Make=HUAWEI                       │
│  │   MakerNote: ##**N4031, Auto              │
│  ├─ APP2 (MPF) <- MPF 多图片目录              │
│  │   NumberOfImages = 2                       │
│  ├─ APP2 (ICC Profile)                        │
│  │   BT.2100 HLG, SMPTE EG 432-1, Full Range │
│  ├─ SOS -> 图像数据 -> EOI (FFD9)              │
├──────────────────────────────────────────────┤ <- 第一 EOI
│  二级数据段                                    │
│  ├─ 第二张 JPEG（含完整 MPF APP2）             │
│  └─ 中间填充 / 私有二进制数据                  │
├──────────────────────────────────────────────┤ <- 嵌入 MP4 起点（搜索 ftypm p42 定位）
│  ╔══════════════════════════════════╗         │
│  ║  嵌入的完整 MP4 文件              ║         │
│  ║  ftyp(mp42) -> mdat -> moov     ║         │
│  ║  Track 1: vide (HEVC)           ║         │
│  ║  Track 2: soun (AAC)            ║         │
│  ║  Track 3: meta (movingphoto)    ║         │
│  ║  udta -> ©too="Openharmony6.1"  ║         │
│  ╚══════════════════════════════════╝         │
├──────────────────────────────────────────────┤ <- moov 结束
│  尾部 (60 bytes)                              │
│  v6_f40  733:1333  LIVE_NNNNNNN              │
└──────────────────────────────────────────────┘ <- EOF

```

#### MPF 多图片结构

一级 JPEG 的 APP2 段包含 MPF（Multi-Picture Format）目录：NumberOfImages=2，MPImage1=Baseline MP Primary Image，MPImage2=Gain Map Image（增益图）。此结构是原生相机 JPEG 实况照片的文件布局特征，与实况照片判定无关。


#### 嵌入 MP4 轨道

与 HEIC 格式共用同一套 MP4 结构（3 track，含 `movingphoto` 标记轨道）。

`LIVE_` 尾部和 HEIC 共用同一套尾部结构。官方 SDK `saveLivePhoto()` 使用简化的 `[JPEG]+[MP4]+[LIVE_尾]` 拼接（无 MPF、无 Track 3），已验证可用。


#### 提取逻辑

```
ftyp_pos = find(data, "ftypmp42")               // 定位嵌入 MP4
video_start = ftyp_pos - 4                       // MP4 box size 字段
moov_pos = rfind(data[video_start:], "moov")     // 找 moov box 尾部
moov_size = read_u32(data, moov_pos - 4)         // moov 字节数
video_end = video_start + moov_pos + moov_size   // MP4 结束位置
video = data[video_start : video_end]             // 完整 MP4
eoi_pos = find_first(data, 0xFFD9)               // 第一个 JPEG EOI
image = data[0 : eoi_pos + 2]                    // 一级 JPEG 图片

```

### 与实况照片无关的华为/荣耀私有数据汇总

以下数据出现在华为/荣耀相机直出文件中，但**均非实况照片功能所需**。合成可用实况照片时无需写入。

### App 操作指南

#### 检测华为实况照片

```
1. 文件末尾搜 "LIVE_" 字节序列
2. 验证 LIVE_ 值 ≈ 嵌入 MP4 大小 + 16（允许小范围浮动）
3. 确认文件内存在嵌入 MP4（搜 "ftypmp42"）
```

#### 提取封面帧（静态图）

```
HEIC: 解析 ISOBMFF → meta → iloc → 提取全分辨率 HEVC 图像 → 转 JPEG/PNG
JPEG: 读取到第一个 FFD9（JPEG EOI），之后的数据是 MP4
```

> 封面帧 = 文件前半段的静态图片。华为没有独立的"封面帧时间戳"——图片本身就是封面帧。

#### 提取视频

```
1. 搜 "ftypmp42" 定位嵌入 MP4 起点（= offset - 4）
2. 搜 "moov" + 读取 moov_size 确定 MP4 终点
3. 提取 [MP4起点 .. moov+moov_size] 即完整视频
```

#### 合成实况照片

```
结构:  [静态图 JPEG/HEIC] + [完整 MP4] + [60B 尾部]

60B 尾部:
  [+0..+5]:   v6_fXX     (XX = 封面帧序号，编辑器进度条读这个)
  [+20..+27]: PPP:QQQQ   (原始封面时间戳:视频时长ms，只读水印)
  [+40..+51]: LIVE_NNNN  (嵌入MP4字节数 + 20)
```

#### 更换封面帧

```
1. 从视频中抽取目标帧 → 编码为 JPEG
2. 替换文件前半段的静态图片
3. 视频保留完整（无需裁切）
4. 更新 fYY = 新封面帧序号
5. 更新 LIVE_ = 新文件布局下的 MP4 字节数 + 20
6. PPP:QQQQ 保持原值不变
```

### 荣耀 Moving Photo

荣耀 Magic 系列（BKQ-AN10 等）的动态照片与华为使用**同一套协议**：JPEG 中段嵌入 MP4 + `LIVE_` 尾标。实况照片的判定、视频定位、拆分逻辑与华为完全一致。

与华为唯一的区别在于尾部结构——荣耀在华为 v2 格式尾部（`vX_fYY  PPP:QQQQ  LIVE_NNNNNNN`）**前面**追加了一段可变长的逐帧防抖矩阵 JSON：

```
uuidextend_type_matrix[{"frameNum":1,"matrixInfo":"{...}"}, ...]
v2_f31              118:1000            LIVE_6251621
└── 荣耀扩展（非实况）──┘└── 与华为相同的 v2 尾部 ──┘

```
JSON 中每个元素对应一个视频帧，记录该帧的 EIS（电子防抖）和 MCTF（运动补偿时域滤波）的 3×3 变换矩阵及画面裁剪参数：

```json
{
  "frameNum": 1,
  "matrixInfo": "{\"decayGain\":1.0,
    \"eis3x3Matrix\":[0.999,-0.043,-41.5,0.043,0.999,17.4,...],
    \"mctf3x3Matrix\":[1.010,-0.008,-125.3,0.009,1.008,161.3,...],
    \"srcDstWh\":[1920,1440,1728,1296]}"
}

```
| 标记 | 说明 | 与实况相关？ |
|------|------|:---:|
| `uuidextend_type_matrix` | 荣耀私有扩展段标识 | 否，视频后处理数据 |
| JSON 内 `eis3x3Matrix` | 逐帧电子防抖矩阵 | 否 |
| JSON 内 `mctf3x3Matrix` | 逐帧运动补偿矩阵 | 否 |
| `vX_fYY` / `PPP:QQQQ` | 华为 v2 格式尾部，与华为含义一致 | ✅ |
| `LIVE_NNNNNNN` | 实况照片判定标记，与华为完全一致 | ✅ |

> 以上 JSON 扩展为荣耀相机 ISP 管线输出的逐帧后处理数据，与实况照片协议无关。仅 `LIVE_` 是实况照片判定标记。

### 三星 Motion Photo

三星 Galaxy 设备的动态照片使用 **双轨制元数据**——同时写入 Google V2 XMP（兼容 Google Photos 等第三方 App）和私有二进制 **Samsung Trailer**（供三星相册使用）。三星相册**完全不读取 XMP**，仅依赖 Trailer 中的 `MotionPhoto_Data` 标签和 SEF 验证区来识别和播放动态照片。

使用者：三星 Galaxy S23 系列及以后、Galaxy Tab S9 系列等。内部格式自称为 **mpv2**（早期）或 **mpv3**（Galaxy S23 Ultra 起）。


#### JPEG 二进制结构

与 Google V2 的关键区别：视频**嵌入在** Samsung Trailer 的 `MotionPhoto_Data` 标签 data 中，而非作为独立数据段追加在 JPEG EOI 之后：

```
┌──────────────────────────────────────┐
│   JPEG 图片                           │
│   (含 V2 XMP: GCamera:MotionPhoto=1   │
│    + Container:Directory)             │
├──────────────────────────────────────┤
│   Samsung Trailer 标签区               │
│   ├─ Image_UTC_Data       (0x0a01)   │
│   ├─ MCC_Data             (0x0aa1)   │
│   ├─ Camera_Scene_Info    (0x0d01)   │
│   ├─ Color_Display_P3     (0x0cc1)   │
│   ├─ Camera_Capture_Mode  (0x0c61)   │
│   ├─ MotionPhoto_Data     (0x0a30)   │  ← MP4 视频在此
│   └─ MotionPhoto_Version  (0x0a31)   │  ← "mpv2" 或 "mpv3"
├──────────────────────────────────────┤
│   SEF 验证区                          │
│   ├─ "SEFH" header                   │
│   ├─ 每个 Tag 的索引条目（offset+size）│
│   └─ "SEFT" footer                   │
└──────────────────────────────────────┘

```

> 整个 Trailer = 标签区 + SEF 区（含视频数据），追加在 JPEG EOI 之后、文件末尾。视频不是独立的顶层数据段——它是 `MotionPhoto_Data` 标签的 data payload。

#### 每个 Tag 的二进制编码

Samsung Trailer 中每个 Tag 的通用编码格式为：

```
偏移    长度    内容
+0      2       0x00 0x00（固定前导）
+2      2       Marker ID（小端序 uint16，如 0x0a30 → 字节 [0x30, 0x0a]）
+4      4       Name 字符串长度（小端序 uint32，含末尾 NUL）
+8      N       Name 字符串（UTF-8，如 "MotionPhoto_Data"）
+8+N    M       Data（M = 该 Tag 的数据长度，由 SEF 索引中的 size 字段给出）
```

例——`MotionPhoto_Data` 标签（JPEG 容器）的二进制编码：
```
00 00  30 0A  10 00 00 00  "MotionPhoto_Data"  <MP4 视频完整二进制>
```


#### 完整 Tag 清单（7 个，按文件内出现顺序排列）

| # | Marker (hex) | Name | 数据内容 | 说明 |
|---|:---:|---|---|---|
| 1 | `0x0a01` | `Image_UTC_Data` | Unix 时间戳（LE u32, 4 字节） | 拍摄时间，无时区信息 |
| 2 | `0x0aa1` | `MCC_Data` | 变长二进制 | 用途未完全文档化（可能与移动国家代码相关） |
| 3 | `0x0d01` | `Camera_Scene_Info` | 变长二进制 | 相机场景信息 |
| 4 | `0x0cc1` | `Color_Display_P3` | 变长二进制 | 广色域 Display P3 色彩标记 |
| 5 | `0x0c61` | `Camera_Capture_Mode_Info` | 变长二进制 | 拍摄模式信息 |
| 6 | `0x0a30` | `MotionPhoto_Data` | **JPEG**: 完整 MP4 视频字节<br>**HEIC**: `"mpv2"` + video_offset(BE u32) + video_size(BE u32) | ★ 核心标签——三星相册视此标签存在与否判定是否为动态照片 |
| 7 | `0x0a31` | `MotionPhoto_Version` | 版本字符串，如 `"mpv2"` 或 `"mpv3"` | 格式版本标识 |


> **ExifTool 映射**：ExifTool 将 marker `0x0a30` 抽象为两个逻辑字段——`EmbeddedVideoType`（值为 name 字符串 `"MotionPhoto_Data"`）和 `EmbeddedVideoFile`（值为 data 部分的视频字节）。但底层二进制仅有 marker + name + data 三段，不存在独立的 "type" 和 "file" 分离存储。

#### SEF 验证区结构

SEF（Samsung Extended Format）位于所有 Tag 之后，是一个自描述索引区。三星相册通过 SEF 快速定位各 Tag 的偏移和长度——**缺少 SEF 区或 SEF 区数据不一致，三星相册将拒绝识别**。

```
偏移        长度        内容
+0          4           "SEFH"（魔数）
+4          4           Version（LE u32，固定为 107）
+8          4           Field Count（LE u32，= 实际写入的 Tag 数量，通常为 7）
+12         N×10        每个 Field 的索引条目：
                        [2B: 0x00 0x00] [2B: marker LE u16] [4B: offset_from_sef LE u32] [4B: size LE u32]
+12+N×10    4           SEF 总大小（LE u32，含此字段自身和 "SEFT"）
+16+N×10    4           "SEFT"（魔数）
```

各 Field 的 `offset_from_sef` 以 SEF 区起始位置（即 "SEFH" 的 +0 字节）为基准——Tag 中偏移值为 0 表示该 Tag 紧接在 SEFT 之后。

#### 与 Google V2 的兼容性（双轨制）

三星原厂文件会**同时写入**两套独立的元数据：

| 层 | 格式 | 用途 |
|---|------|------|
| **XMP** | Google MotionPhoto V2（`GCamera:MotionPhoto=1` + `Container:Directory`） | 兼容 Google Photos、Windows 资源管理器等第三方 App |
| **Trailer** | Samsung Private Trailer（7 Tags + SEFH/SEFT） | **三星相册唯一识别方式** |

关键事实：
- **三星相册完全不读取 XMP**，仅凭 Trailer 判定动态照片
- **Google Photos 不读取 Samsung Trailer**，仅凭 V2 XMP 判定
- 合成三星兼容的动态照片**必须同时写入两套元数据**，缺一不可

#### Motion Photo v3（mpv3）

较新的三星设备（Galaxy S23 Ultra、Tab S9 等）在 `MotionPhoto_Version` 标签中写入 `"mpv3"` 而非 `"mpv2"`。两种版本的 Trailer 和 SEF 结构完全一致，仅版本字符串不同。MotionPhoto2 工具默认生成 `"mpv3"` 格式。

#### HEIC 容器：mpvd 与 sefd box

当容器为 HEIC 时，三星不使用 JPEG Trailer 追加方式，而是通过两个私有 **ISOBMFF 顶层 box** 封装动态照片数据：

```
┌──────────────────────────────────────┐
│   HEIC 静态图片 (ftyp + meta + mdat)  │
│   (meta box 内含 V2 XMP)              │
├──────────────────────────────────────┤
│   mpvd box (Motion Photo Video Data) │
│   ├─ 4B: box size (BE u32)           │
│   ├─ 4B: "mpvd"                      │
│   ├─ MP4 视频原始字节                  │
│   └─ sefd box (嵌套在 mpvd 内部)      │
│       ├─ 4B: box size (BE u32)       │
│       ├─ 4B: "sefd"                  │
│       ├─ Tag 数据区（格式同 JPEG，     │
│       │   但 MotionPhoto_Data 不含视频）│
│       └─ SEFH/SEFT 验证区             │
└──────────────────────────────────────┘

```

**HEIC 与 JPEG 的关键区别**：

| 方面 | JPEG | HEIC |
|------|------|------|
| 视频位置 | 在 Trailer 的 `MotionPhoto_Data` data 中 | 在 mpvd box 中（sefd 之前） |
| `MotionPhoto_Data` 内容 | 完整 MP4 视频字节 | `"mpv2"` + video_offset(BE u32) + video_size(BE u32)（12 字节指针） |
| 视频偏移基准 | SEF 区起始（"SEFH" 位置） | mpvd box 起始 |
| 容器级标识 | 无 | mpvd + sefd box 名 |
| XMP Primary Padding | 0 | 8（= mpvd 头部 8 字节） |

> HEIC 下的 `MotionPhoto_Data` data 为 `"mpv2"`（4 字节）+ 视频在 mpvd box 内的字节偏移（BE u32）+ 视频字节长度（BE u32），共 12 字节。三星相册据此在 mpvd box 内定位视频数据。


#### 提取逻辑

1. 使用 ExifTool 提取视频：`exiftool -b -EmbeddedVideoFile > video.mp4`
   （ExifTool 自动解析 Samsung Trailer，抽取 `0x0a30` 标签的 data 部分）
2. 使用 ExifTool 提取完整 Trailer：`exiftool -b -trailer > out.bin`
3. 手动替换视频需同步更新：
   - `MotionPhoto_Data` 的 data 部分（新视频字节）
   - SEF 索引中 `0x0a30` 条目的 size 字段
   - 所有后续 Tag 的 offset 字段
   - 简单截断并追加新 MP4 **会被三星相册拒绝**
4. HEIC 文件中的提取：搜索 `"mpvd"` box → 解析内部 sefd → 根据 `MotionPhoto_Data` 中的 offset/size 指针定位视频


#### 合成实用性结论

- 合成三星兼容的动态照片需要**同时满足**：
  - **Samsung Trailer**（7 Tags + SEFH/SEFT）——供三星相册识别
  - **Google MotionPhoto V2 XMP**（`GCamera:MotionPhoto=1` + `Container:Directory`）——供 Google Photos 等第三方 App 识别
- Google Gallery 额外要求文件名以 `"MV"` 开头
- 参考实现：[PetrVys/MotionPhoto2](https://github.com/PetrVys/MotionPhoto2)（Python，完整处理 JPEG 和 HEIC 两种容器，默认生成 mpv3）
- Trailer 内部偏移量和 SEF 索引有严格的交叉引用关系，手动拼接极易出错，推荐程序化生成

## 📁 双文件格式


### Apple Live Photo


#### 文件结构

iPhone 拍摄的实况照片由两个独立文件组成：

```
IMG_1234.HEIC  — 静态照片（HEIF 容器，含封面帧图像）
IMG_1234.MOV   — 动态视频（QuickTime 容器，约 3 秒，含音频轨）

```

#### 配对机制：ContentIdentifier

两个文件存储相同的 `ContentIdentifier` UUID。此 UUID 由 iPhone 在拍摄时生成，写入 QuickTime 顶级元数据：

```
IMG_1234.HEIC → ContentIdentifier = "D4E5F6A7-89AB-4CDE-..."
IMG_1234.MOV  → ContentIdentifier = "D4E5F6A7-89AB-4CDE-..."  （完全一致）

```
配对优先级：ContentIdentifier UUID > 文件名 > 拍摄日期+GPS 兜底。


#### HEIC 文件中的实况照片相关元数据

| 元数据字段 | 位置 | 说明 |
|-----------|------|------|
| `ContentIdentifier` | MakerNotes (QuickTime) | **配对 UUID**，与 MOV 中的一致。由 iPhone 拍摄时生成，四组样本验证全部精确匹配 |
| `Live Photo Video Index` | MakerNotes | **实况照片视频索引**，Apple 私有整数。四组样本中同一设备该值固定（8595185700），不同设备值不同 |
| `Image Capture Type` | MakerNotes | 拍摄模式，实况照片固定为 `Scene` |
| `Photo Identifier` | MakerNotes | 照片自身 UUID，与 ContentIdentifier 不同。同一连拍会话中多张照片共享此值 |
| `QuickTime:Rotation` | QuickTime 元数据 | 旋转方向（如 `Rotate 90 CW`） |
| `EXIF:Orientation` | EXIF IFD | EXIF 方向标签。可能与 `Rotation` 不一致——这是方向异常的根源 |

> `Orientation` 列为实况照片相关字段的原因：它与 QuickTime 的 `Rotation` 经常冲突，直接影响封面帧显示方向。


#### MOV 文件中的实况照片相关元数据

| 元数据字段 | 位置 | 说明 |
|-----------|------|------|
| `ContentIdentifier` | QuickTime 顶级 | **配对 UUID**，与 HEIC 中的一致 |
| `ContentDescribes` | QuickTime 顶级 | **指向视频轨道**，始终为 `Track 1` |
| `Make` | QuickTime 顶级 | 设备制造商，`Apple` |
| `Model` | QuickTime 顶级 | 设备型号，如 `iPhone 16 Pro Max` |
| `LivePhotoAuto` | QuickTime 顶级 | **实况照片自动标记**，值为 `1`。四组样本全部一致 |
| `LivePhotoVitalityScore` | QuickTime 顶级 | 活力评分，0~1 之间。描述视频中动作的活跃程度，各样本不同 |
| `LivePhotoVitalityScoringVersion` | QuickTime 顶级 | 活力评分算法版本，当前为 `4` |
| `PosterTime` | QuickTime Movie 级别 | 始终为 `0 s`，**不反映真实封面帧位置** |
| `StillImageTime` | Metadata 轨道（mebx） | 值为 `-1`，**标记哪个轨存储了封面帧**。该轨的 `TrackDuration` 才是封面帧在视频中的实际秒数 |
| `QuickTime:Matrix` | Movie 级别 | 3×3 仿射变换矩阵（通常 identity） |
| `QuickTime:Matrix` | Track 1 级别 | 视频轨的 3×3 旋转矩阵 |
| `MediaDuration` | Track 1 | 视频时长（秒），通常 2.7~3.0 秒 |


#### MOV 轨道结构

经 Live Photo Box 加工后仍能被 iOS 识别的最小结构（Next Track ID = 5，即 4 个轨道）：

| Track ID | 类型 | Handler | 说明 |
|:---:|------|------|------|
| 1 | Video Track | Core Media Video | 视频轨，HEVC (hvc1) 编码，含旋转矩阵 |
| 2 | Audio Track | Core Media Audio | 音频轨 |
| 3 | NRT Metadata | Core Media Metadata | 元数据轨，`ContentDescribes` 指向 Track 1 |
| — | Alias Data | Core Media Data Handler | 每个媒体轨各带一个数据处理器 |

> 原始 iPhone MOV 有 11~12 个轨道（Next Track ID=12），包含多个 Auxiliary Picture 轨道（sky map、person map、skin map 等，供 Apple 后期算法使用）。但这些轨道对实况照片的识别和播放**不是必需的**——4 轨最小结构已验证可行。


#### 封面帧机制

与 Google/OPPO 用微秒时间戳指向视频中某一帧不同，Apple 的封面帧位置藏在 MOV 文件的 **Timed Metadata 轨道**（mebx 类型）中。具体机制：

1. MOV 的 Movie 级别 `PosterTime` **始终为 0**，不反映实际封面位置
2. 封面帧作为**嵌入的静态图像**存储在某个 metadata 轨里，该轨带有 `StillImageTime = -1` 标记
3. **该轨的 `TrackDuration` 即封面帧在视频时间轴上的位置**（秒）

例如原始 iPhone 直出的 MOV：
- Track 10 有 `StillImageTime: -1`，`TrackDuration: 1.37 s` → 封面帧在视频第 1.37 秒

更换封面后：
- StillImageTime 轨变到 Track 4，`TrackDuration: 2.23 s` → 封面帧被改到了第 2.23 秒

更换封面帧时，需要更新该 metadata 轨的静态图像数据和时间偏移。


#### 创建 Apple 兼容实况照片的最低要求

基于样本验证，iOS 识别一组文件为实况照片至少需要：

**照片端**（HEIC）：

- `ContentIdentifier` UUID
- `Live Photo Video Index`（Apple MakerNote 私有整数）
- `Image Capture Type = "Scene"`
- `Make = "Apple"`

**视频端**（MOV）：
- `ContentIdentifier` UUID（与照片一致）
- `ContentDescribes = "Track 1"`
- `Make = "Apple"`, `Model = "iPhone XX"`
- `LivePhotoAuto = 1`
- 最小轨道结构：Video Track + Audio Track + Metadata Track


#### QuickTime 旋转矩阵

Apple 使用 3×3 仿射变换矩阵表示视频方向，而非单一角度值：

| 矩阵 | 含义 | 等效旋转 |
|------|------|:---:|
| `[1 0 0 · 0 1 0 · 0 0 1]` | 正常 | 0° |
| `[0 1 0 · -1 0 0 · 0 0 1]` | 正手持拍摄 | 顺时针 90° |
| `[-1 0 0 · 0 -1 0 · 0 0 1]` | 倒置拍摄 | 180° |
| `[0 -1 0 · 1 0 0 · 0 0 1]` | 反手持拍摄 | 顺时针 270° |
| `[1 0 0 · 0 -1 0 · 0 0 1]` | 前置摄像头翻转 (A) | 0°（上下镜像） |
| `[-1 0 0 · 0 1 0 · 0 0 1]` | 前置摄像头翻转 (B) | 180°（上下镜像） |

数值可能以普通整数（-1, 0, 1）或 16.16 定点数（65536=1.0, 16384=0.25）表示。


#### 常见问题

| 问题 | 原因 | 表现 |
|------|------|------|
| 缩略图横向拉伸 | iOS 17.3 之前 Apple 嵌入低分辨率缩略图但保留方向标签 | Windows 将其当作横向图片，导致宽高比错误 |
| 前置摄像头视频旋转异常 | 前置摄像头纵向像素横向存储，方向由旋转矩阵指示 | Windows 不读取 QuickTime 旋转矩阵，视频方向错误 |
| HEIC 方向不一致 | EXIF `Orientation` 与 `QuickTime:Rotation` 标注不同 | 不同软件读取不同标签，显示方向各异 |
| ContentIdentifier 丢失 | 跨平台传输时部分工具不保留 QuickTime 元数据 | 照片与视频配对关系断裂 |

### <a id="vivo-x200"></a>vivo Live Photo（≤X200 系列）

早期 vivo 实况照片采用双文件 + 私有 JSON 尾标的方案。实测 iQOO 12（OriginOS 4）。


#### 文件结构

一张 `.jpg` + 一个 `.mp4`，两者文件名前缀相同，存放在同一目录下。删除 `.mp4` → 失去动态效果。


#### 配对机制

两个文件**各自**在尾部携带一份私有 JSON，vivo 相册通过 `com.android.camera.livephoto` 字段的值进行配对。JSON 中其余字段均为 vivo 相机私有数据（设备信息、拍摄参数等），与实况照片识别无关。

**JPEG 尾部** — 文件末尾，格式为 `vivo{JSON}cameralbum!`：

```
vivo{"com.android.camera.hdr":49426,
     "com.android.camera.joint.fullview.orientation":0,
     "com.android.camera.fisheye":-1,
     "com.android.camera.takenmodel":"iQOO 12",
     "com.android.camera.camerafacing":"0",
     "com.android.camera.livephoto":"1781689481524ba274bd00000000",
     "version":2104,
     ...}
cameralbum!

```
**MP4 尾部** — ISOBMFF `uuid` box（user type = `vivoMediaExtInfo`），同样包含 `vivo{JSON}`：

```
vivo{"com.android.camera.takenmodel":"iQOO 12",
     "com.android.camera.camerafacing":"0",
     "com.android.camera.imageTime":0,
     "com.android.camera.moduleid":"photo",
     "com.android.camera.livephoto":"1781689481524ba274bd00000000",
     "version":2104,
     "com.android.camera.faceInfo":{}}

```
| 字段 | 位置 | 说明 | 与实况相关？ |
|------|------|------|:---:|
| `com.android.camera.livephoto` | JPEG + MP4 | 实况照片配对 ID，两端一致 | ✅ |
| `cameralbum!` | 仅 JPEG | 尾部标记，标识此文件为实况照片 JPEG | ✅ |
| `uuidvivoMediaExtInfo` | 仅 MP4 | ISOBMFF box，标识此文件为实况照片 MP4 | ✅ |
| `com.android.camera.takenmodel` | JPEG + MP4 | 设备型号 | 否 |
| `com.android.camera.camerafacing` | JPEG + MP4 | 摄像头方向 | 否 |
| `com.android.camera.moduleid` | JPEG + MP4 | 拍摄模块（`"photo"`） | 否 |
| `version` | JPEG + MP4 | 格式版本号，因设备而异 | 否 |
| `com.android.camera.imageTime` | 仅 MP4 | 图片时间戳 | 否 |
| `com.android.camera.faceInfo` | 仅 MP4 | 人脸检测数据 | 否 |
| `com.android.camera.hdr` | 仅 JPEG | HDR 模式参数 | 否 |
| `com.android.camera.fisheye` | 仅 JPEG | 鱼眼镜头参数 | 否 |
| `com.android.camera.joint.fullview` | 仅 JPEG | 全屏取景标记 | 否 |
| `com.android.camera.joint.fullview.orientation` | 仅 JPEG | 取景方向 | 否 |
| `com.vivo.xdr.maxGain` | 仅 JPEG | XDR 增益值 | 否 |
| `com.android.camera.watermarkVersion` | 仅 JPEG | 水印版本 | 否 |
| `com.android.camera.project` | 仅 JPEG | 内部项目代号 | 否 |

> 🔴 以下字段仅在社区参考中出现过（iQOO 7），实测 iQOO 12 不存在，是否为固定字段待确认：
> - `com.android.camera.document` — 文档扫描模式
> - `com.android.camera.joint.conshoot` — 连拍标记
> - `com.android.camera.joint.motioncapture` — 🔴 名字含 "motion"，推测与动态拍摄有关，但值为 `0` 且在 iQOO 12 缺失，实况照片功能不依赖它


#### 实用性结论

旧格式跨品牌兼容性极差，已被 X300 系列单文件 V2 取代，不建议基于此格式开发。

## 🔍 检测与识别


### 单文件格式（Google V2 / OPPO O-Live / 小米 Mi-Live / vivo Live）

读取 JPEG 文件前 1 MB，搜索以下特征字符串：

**Google MicroVideo V1**:
- `GCamera:MicroVideo="1"`
- `GCamera:MicroVideoOffset`

**Google MotionPhoto V2**:
- `GCamera:MotionPhoto="1"`
- `Container:Directory`
- `Item:Semantic="MotionPhoto"`

**OPPO O-Live Photo**（兼容 V2，额外检测以下标记）:
- `OpCamera:MotionPhotoOwner="oplus"`
- `xmlns:OpCamera`
- EXIF `UserComment` 以 `oplus_` 开头

**小米 Mi-Live Photo**（就是 Google V2，额外检测私有标签以区分来源）:
- `MiCamera:XMPMeta`（`video_madrid_image`，旧样本为 `MiCamera:VideoLength`）

**vivo Live Photo**（X300 系列起就是 Google V2，额外检测 VCamera 以区分来源）:
- `VCamera:VMotionPhotoVersion`
- `xmlns:VCamera`

**三星 Motion Photo**（双轨制：V2 XMP 兼容 Google Photos + 私有 Trailer 供三星相册）:

- Samsung Trailer 中包含 `MotionPhoto_Data` 标签（marker `0x0a30`）及其 data 部分（视频）
- SEF 验证区魔数 `SEFH` / `SEFT` 存在且索引一致
- HEIC 容器中检测 `mpvd` / `sefd` box
- 同时满足 MotionPhoto V2 XMP 字段（`GCamera:MotionPhoto` + `Container:Directory`，供 Google Photos 兼容）

**华为 Moving Photo（HEIC）**:

- 文件尾部搜索 `LIVE_` 字节序列 ← 唯一必需标记
- 搜索第二个 `ftyp` box（major=`mp42`）= 嵌入 MP4 存在
- MP4 moov 中存在 `com.openharmony.timed_metadata.movingphoto` 轨道（辅助，非必需——连拍模式无此轨道仍为实况）
- ⚠️ `tmap` brand 不是实况照片标记（所有华为相机 HEIC 均有，包括非实况）

**华为 Moving Photo（JPEG）**:
- 文件尾部搜索 `LIVE_` 字节序列 ← 必需
- 文件内搜索嵌入的 `ftypmp42` 字节序列 ← 必需（标记 MP4 视频嵌入位置）
- `Make = "HUAWEI"` + 文件体积 > 3MB（辅助判断）
- 干净 MP4（无 com.openharmony keys、无 Track3）+ `LIVE_` 尾标即可正常播放，与官方 SDK `saveLivePhoto()` 行为一致

**荣耀 Moving Photo**（与华为相同协议）:
- 文件尾部搜索 `LIVE_` 字节序列
- 文件内搜索嵌入的 `ftypmp42` 字节序列
- `Make = "HONOR"` + 文件体积 > 3MB（辅助判断）

**华为 — Android MediaStore**:
- 查询 `special_file_type = 50 OR special_file_type = 1050`（官方 LivePhotoKit SDK 文档确认）

命中任一标记即可判定为候选。进一步解析视频偏移量/长度，验证数值合理性（>4KB、<文件总大小），即可确认。

> 注意：
> - Google/OPPO 的命名空间 URI 在不同设备/系统版本间存在格式差异（空格、引号、`http` vs `https`），因此直接搜索**短属性名**（如 `GCamera:MotionPhoto`）兼容性最好，不建议精确匹配完整 URI。
> - 华为不使用 XMP，因此 XMP 搜索对其无效。必须使用尾部扫描（`LIVE_`）或盒子结构解析（`ftypmp42` 定位）。

### 双文件格式（Apple Live / vivo Live ≤X200）

**Apple — 文件名配对**

扫描目录中扩展名基础部分相同的 `.heic`/`.jpg` 与 `.mov`/`.mp4` 文件，初步配对。
